# תפעול: מדריך למי שמחזיק את הכלי

הדף הזה לאדם או לצוות שמקבל את הכלי לידיים: איפה הוא רץ, איך מעדכנים אותו, ומה בודקים אחרי כל פריסה. ארבעת הסעיפים האחרונים (הריצה הלילית, טוקן, שנה חדשה, תוכנית חדשה) הם התפעול השוטף של בעלי הריפו.
איך מריצים ובודקים מקומית: [DEVELOPING](DEVELOPING.md). אבטחה ופרטיות: [SECURITY](SECURITY.md). מבנה הקוד: [ARCHITECTURE](ARCHITECTURE.md).

## אירוח

האתר הוא תיקיית `web/`: קבצי HTML, CSS ו-JavaScript (ES modules) וקובצי JSON. אין build, אין קוד שרת ואין מסד נתונים; כל מה שהמשתמש שומר נשאר ב-localStorage של הדפדפן שלו.

- **אפשר לארח בכל שרת קבצים סטטי.** מעתיקים את תוכן `web/` לשורש כתובת (או לתת-תיקייה: הנתיבים באתר יחסיים) ומגישים אותו. כרגע הוא מוגש מ-GitHub Pages: [deploy.yml](../.github/workflows/deploy.yml) מריץ `npm test` ורק אחריו מעלה את `web/`, בכל push ל-`main` שנוגע ב-`web/**`.
- **HTTPS הכרחי.** העתקת קישור ושיתוף (`navigator.clipboard`, `navigator.share`) עובדים רק בהקשר מאובטח.
- **סוג התוכן של קבצי `.mjs`** חייב להיות JavaScript (`text/javascript`). שרת שמחזיר להם `application/octet-stream` שובר את הסיור ואת ייבוא ה-PDF (ראו "אחרי כל פריסה").
- **מדיניות האבטחה (CSP) כתובה בתוך ה-HTML** (תג `<meta http-equiv="Content-Security-Policy">` ב-`index.html` וב-`legal.html`), ולכן אין צורך להגדיר כותרות בשרת. פירוט ב-[SECURITY](SECURITY.md).
- **מעבר לכתובת אחרת:**
  - מחליפים את הכתובת הקבועה ב-`web/index.html` (`og:url` ו-`og:image`, שורות 18 ו-21) ואת קישורי ה-issues ב-`web/index.html` וב-`web/legal.html`. בקבצי `web/*.js` הנתיבים יחסיים.
  - הבדיקה [test/app.test.mjs:164](../test/app.test.mjs) מקודדת את `https://lets-learn-il.github.io/og.png`. מעדכנים גם אותה, אחרת `npm test` והפריסה נכשלים.
  - הכתובת הישנה מופיעה גם ב-`README.md`, ב-`TERMS.md` וב-[.github/ISSUE_TEMPLATE/config.yml:4](../.github/ISSUE_TEMPLATE/config.yml).
  - ב-[scripts/check-fresh.mjs:7](../scripts/check-fresh.mjs) הכתובת קבועה. בלי לעדכן אותה, בדיקת הדופק ממשיכה לבדוק את הכתובת הישנה.
  - העברת הריפו לחשבון אחר משנה גם את כתובת ה-clone של הריצה הלילית ([ci/gitlab-scrape.yml](../ci/gitlab-scrape.yml)) וגם את ה-`include` בפרויקט בגיטלאב, ודומיין לא פותר את זה.
  - ה-localStorage שייך לכתובת (origin), ולכן הנתונים ששמרו הסטודנטים **לא עוברים** לכתובת החדשה. לפני המעבר מבקשים מהם לייצא גיבוי (קישור גיבוי) ולפתוח אותו בכתובת החדשה.
- **נתונים:** הקבצים ב-`web/data/afeka/`. מי מייצר אותם: הסורק של המאגר (הריצה הלילית, בהמשך הדף), או ייצוא רשמי של המכללה.

## עדכון נתונים

1. **מהסורק:** הריצה הלילית בגיטלאב דוחפת קבצים חדשים ל-`web/data/afeka/`, ו-push כזה מפעיל פריסה. אין מה לעשות ביד.
2. **מייצוא רשמי:** מניחים את הקבצים בתיקייה נפרדת, במבנה של [DATA-CONTRACT](DATA-CONTRACT.md), ובודקים:

   ```
   npm run check:export -- <תיקיית הייצוא>
   npm run check:export -- <תיקיית הייצוא> --against web/data/afeka
   ```

   שגיאה (`ERROR:`) מחזירה קוד יציאה 1. אזהרה לא עוצרת. עם `--against` הבדיקה משווה לנתונים שעל האתר ומזהירה על ירידה חדה במספר הקורסים, הקבוצות והבחינות. כשהפלט הוא `ok` מעתיקים את התיקייה לתוך `web/data/afeka/`, מריצים `npm test` ופורסים.
3. האתר מבקש את הנתונים עם `cache: 'no-cache'` (בדיקת ETag), כך שגרסה חדשה מופיעה בביקור הבא בלי לנקות מטמון.

## web/settings.json

קובץ ההגדרות שמי שמחזיק את הכלי עורך ביד: [web/settings.json](../web/settings.json). האתר טוען אותו בכל כניסה ומנקה אותו שדה אחר שדה ב-`cleanSettings` ([web/settings.js](../web/settings.js)). שדה חסר או בסוג הלא נכון חוזר לברירת המחדל, ולכן קובץ שגוי לא שובר את האתר. מצד שני, ערך לא תקין פשוט **לא מוצג**, בלי הודעה. אחרי כל עריכה פותחים את האתר ובודקים שהערך מופיע.

הדוגמאות הן קטעים מתוך הקובץ; משלבים אותן באותו אובייקט. אחרי עריכה: `npm test` ([test/settings.test.mjs](../test/settings.test.mjs) קוראת את הקובץ), ואז commit ופריסה.

### notice: הודעה בראש האתר

טקסט חופשי שמופיע כרצועה אדומה (`role="alert"`) בראש האתר, לכל המשתמשים, עד שמרוקנים אותו. טקסט בלבד, בלי HTML. `""` מכבה אותה.

```json
{ "notice": "הנתונים של סמסטר ב׳ יתעדכנו מחר בבוקר" }
```

### turns: תורי הרשמה

רשימת התורים שהסטודנט בוחר ב"המצב שלי" ("התור שלי בהרשמה"). כשהתור שבחר כבר נפתח, והנתונים נמשכו לפני שנפתח, מוצגת האזהרה "הנתונים נמשכו לפני פתיחת התור שלך".

```json
{
  "turns": [
    { "id": "year-4", "label": "שנה ד׳", "opensAt": "2026-09-01T09:00:00+03:00" },
    { "id": "year-3", "label": "שנה ג׳", "opensAt": "2026-09-02T09:00:00+03:00" }
  ]
}
```

- `id`: מחרוזת עד 40 תווים. אל תשנו `id` אחרי שפורסם: הוא נשמר אצל הסטודנטים.
- `opensAt`: רגע עם אזור זמן (`+03:00` או `Z`), לא תאריך בלבד. תור בלי אזור זמן, בלי `id` או בלי `label` נזרק.
- בלי תורים אין בחירת תור ב"המצב שלי".

### examsNote: מאיפה מועדי הבחינות

מוצג ליד מועדי הבחינות, כשמוצג לפחות מועד אחד. מועד מטבלת הבחינות (`S_EXAMS`) קודם למועד מדף קורס שהריצה הלילית קוראת ממילא, וזה קודם למשיכה הידנית. האתר לא מבדיל ביניהם, ולכן הנוסח צריך לומר על איזה מועדים הוא מדבר. מי שמושך את המועדים מחדש (`scripts/pull-exams.mjs`) מעדכן גם את התאריך כאן.

```json
{ "examsNote": "מועד שלא פורסם בטבלת הבחינות נמשך ידנית מדף הקורס ב-2.11.2026" }
```

### supportEmail: כתובת לדיווח על טעות

כתובת אחת. מופיע קישור "דיווח על טעות" שפותח מייל עם התוכנית, המחזור, הסמסטר והקבוצה. ריק: אין קישור. הכלל ([web/settings.js:4](../web/settings.js)): כתובת אחת עם `@` אחד בדיוק, בלי רווח ובלי `< > " , % ? & #`, ולא בדומיין שמור לדוגמאות (`example.com`, `.test` וכדומה). כתובת שלא עומדת בו נפסלת בשקט.

```json
{ "supportEmail": "<כתובת התמיכה>" }
```

(בקובץ האמיתי מחליפים ב-`name@example.com` אמיתית.)

הכתובת כתובה גם בעמוד הנגישות ויצירת הקשר ב-`web/legal.html` כטקסט קבוע. מחליפים בשני המקומות, ובדיקה ב-`test/settings.test.mjs` נכשלת אם הם לא זהים. התיבה היום היא חשבון Gmail ייעודי, והיא חלק ממה שמעבירים למי שמקבל את הכלי.

### counselingUrl: דף הייעוץ של המכללה

כתובת `https://` בלבד. מופיע קישור לייעוץ בתחתית האתר ובהערת התוצאות. ריק, `http://` או `javascript:`: אין קישור.

```json
{ "counselingUrl": "https://www.example.ac.il/counseling" }
```

### programs[id].approved: אישור מחלקה

`id` הוא מספר התוכנית (מפתח ב-[scripts/programs.json](../scripts/programs.json)), ובתוכו שנת מחזור ותאריך `YYYY-MM-DD`. לאותה תוכנית ומחזור מופיע "אושר על ידי המחלקה, 5.10.2026", והוא מסומן גם בדוח הכללים (בהמשך).

```json
{ "programs": { "30": { "approved": { "2026": "2026-10-05" } } } }
```

תאריך בפורמט אחר (`5.10.2026`, `2026-1-5`), חודש או יום מחוץ לטווח (`2026-13-01`) ושנה שאינה ארבע ספרות נזרקים. יום שאינו קיים בחודש (`2026-02-31`) לא נבדק, ובמנוע ה-JavaScript שבו נבדקה התוכנית הוא עובר; התוצאה תלויה במנוע ולכן אי אפשר לסמוך עליה. כותבים תאריך אמיתי.

### programs[id].conflicts: סתירות בין מקורות רשמיים

סתירה בין תוכנית הלימודים לידיעון. מופיעה ב"המצב שלי" למחזורים שברשימה, ומזינה את דפי הסתירות (`npm run report:conflicts`).

**דוגמה בלבד, לא להעתיק כמות שהיא:** המספרים והרשימה בדוגמה בדויים. כותבים סתירה אמיתית שנמצאה במקורות.

```json
{
  "programs": {
    "30": {
      "conflicts": [
        {
          "cohorts": [2026, 2027],
          "text": "נ״ז הבחירה (תוכנית הלימודים: 20, הידיעון: 18)",
          "plan": "20 נ״ז בחירה",
          "yedion": "18 נ״ז ברשימה 30009",
          "tool": "הולך לפי הידיעון: 18 נ״ז"
        }
      ]
    }
  }
}
```

- `cohorts`: רשימה לא ריקה של שנות מחזור (מספרים שלמים). `text`: עד 300 תווים, **בלי `.` `!` או `?` בסוף** (האתר מוסיף נקודה; הבדיקה ב-[test/settings.test.mjs:98](../test/settings.test.mjs) נכשלת אם `text` של סתירה בקובץ מסתיים באחד מהם). **סתירה שה-`text` שלה ארוך מ-300 תווים נזרקת כולה.**
- `plan`, `yedion`, `tool`: אופציונליים, עד 300 תווים כל אחד. ארוך מדי: רק העמודה נשמטת והסתירה נשארת. עמודה חסרה מודפסת בדף כ"לבדיקת המחלקה".
- כשהמחלקה מכריעה: מוחקים את הסתירה מהקובץ, גם אם זו האחרונה של התוכנית. הבדיקה ("the shipped settings.json" ב-[test/settings.test.mjs](../test/settings.test.mjs)) בודקת שכל סתירה שנשארה עברה את הניקוי ומציינת מחזורים קיימים, ואין רשימה שצריך לעדכן בה.

## בדיקות ודוחות

- `npm test`: בדיקות היחידה (`node --test "test/*.test.mjs"`). כוללות את הקריאה של `settings.json`, את מדיניות ה-CSP, את אורך השורות ב-`web/` (עד 160 תווים, 200 בשורה של מחרוזת תבנית או HTML) ואת הסורק. חייב להיות ירוק לפני כל פריסה (גם `deploy.yml` מריץ אותו).
- `npm run test:browser`: דפדפן אמיתי (Playwright WebKit): נגישות (axe), זרימות מלאות והסיור. דורש `npm ci` והתקנת הדפדפן של Playwright.
- `npm run report:rules`: דף A4 לכל תוכנית ומחזור עם הרשימות, הנ״ז ודרישות הקדם שהכלי קורא, וקו חתימה למחלקה, ב-`out/rules/` (`index.html` הוא התוכן). קורא רק את `web/data/afeka/` ואת `settings.json`, בלי רשת.
- `npm run report:conflicts`: דף אחד לכל מחלקה שיש לה סתירה פתוחה, ב-`docs/conflicts/<מספר מחלקה>.html` (נשמר ב-git, כדי לעקוב אחרי הפערים עד שהמחלקה עונה), עם עמודה ריקה להחלטה. נבנה מ-`programs[id].conflicts`.
- התיקייה `out/` לא נכנסת ל-git (`.gitignore`). פותחים את הקובץ בדפדפן ומדפיסים.

## אחרי כל פריסה

מחליפים `<site>` בכתובת האתר:

1. הדף עולה, ואין בו רצועה אדומה (`notice`) שלא תכננתם.
2. `curl -s <site>/settings.json` מחזיר את הקובץ שערכתם.
3. `curl -I <site>/vendor/driver/driver.js.mjs` חייב להחזיר `200` ו-`Content-Type` של JavaScript (`text/javascript` או `application/javascript`). אחרת הסיור נעלם בשקט: אין שגיאה, פשוט אין סיור ([web/tour.js](../web/tour.js) מדלג עליו כשהמודול לא נטען). לאותה סיבה בודקים גם `<site>/vendor/pdfjs/pdf.min.mjs` (ייבוא ציונים).
4. `curl -I <site>/data/afeka/catalog.json` מחזיר `200`.
5. בדפדפן: בוחרים תוכנית ומחזור, ורואים קורסים ולוח.

## הריצה הלילית

**GitLab מפעיל בדיקה ב-GitHub בתוך חלונות הפרסום:** העבודה `dispatch` ב-[ci/gitlab-scrape.yml](../ci/gitlab-scrape.yml) שולחת אירוע `repository_dispatch` מסוג `pull-check` אל [.github/workflows/nightly.yml](../.github/workflows/nightly.yml). חלונות הפרסום הם 01:30–04:30 ו-14:30–17:30 בישראל, לפי `Asia/Jerusalem`, כולל שעון קיץ וחורף; שעת הסיום אינה כלולה. הבדיקות מתוכננות ל-01:40, 02:40, 03:40, 14:40, 15:40 ו-16:40. הבדיקה השעתית של GitHub בדקה 37 (`37 * * * *`) נשארת כגיבוי, כי GitHub יכול לעכב ריצות מתוזמנות או לדלג עליהן. שני סוגי האירועים עוברים את אותן בדיקות זמן ונתונים; קבלת האירוע אינה מבטיחה שהסריקה התחילה.

להגדרת לוח הזמנים הנוסף ב-GitLab, בפרויקט `lets_learn-scrape`: Build → Pipeline schedules → New schedule. התיאור הוא `GitHub pull check`, ה-cron הוא `40 1,2,3,14,15,16 * * *`, ואזור הזמן הוא `Asia/Jerusalem`. יש לבחור את הענף המוגן שבו מוגדר ה-include לקובץ ה-CI, כדי שהמשתנה המוגן `GH_PUSH_TOKEN` יהיה זמין. בשדות Variables יש להוסיף `ROLE` בערך `dispatch` ולסמן Active להפעלת הלוח. זהו משתנה סביבה של הלוח, ולא Input. יצירת הלוח והפעלתו נעשות בנפרד משינוי הקוד. לוח הגיבוי הקיים, שמספרו `4470015`, נשאר כפי שהוגדר, בלי `ROLE`; אין צורך לשנות את זמניו או את מצב הפעילות שלו.

בלוח עם `ROLE=dispatch` פועלת רק עבודת `dispatch`, בלי checkout או התקנת תלויות. היא משתמשת ב-`GH_PUSH_TOKEN` הקיים, עם הרשאת Contents לקריאה וכתיבה לאותו ריפו; אין צורך בטוקן נוסף. תשובה שאינה HTTP 204, או כשל רשת, מכשילים את העבודה וגורמים להתראת הכישלון של GitLab להישלח במייל. המייל עשוי להעיד ש-GitHub דחה את הטוקן כי פג או בוטל, שדחה את הבקשה מסיבה אחרת, או שלא היה זמין. ביומן מופיע קוד HTTP, בלי הטוקן. בשעה 01 בישראל נבדקת גם כותרת תוקף הטוקן מאותה תשובה; פחות מ-14 יום מכשילים את העבודה עם הפניה לחידוש, גם אם האירוע כבר התקבל. אם הכותרת חסרה, נרשם שאין תאריך בתשובה. כשל בשליחה משאיר את בדיקת ה-cron של GitHub ואת התראת הטריות כגיבוי.

בחלון מתחילים ניסיון אחד אם לא התחילה בו סריקת פרסום, ובכל מקרה נשמר מרווח של לפחות שלוש שעות בין התחלות. אם `checkedAt` שפורסם ב-main ישן מ-20 שעות, חסר או לא תקין, אפשר להשלים סריקה בכל שעה, גם באותו חלון, לאחר מרווח של שלוש שעות. כישלון אינו גורר ניסיון מדי שעה: הניסיון הבא אפשרי בחלון הבא או אחרי שלוש שעות כשהנתונים עדיין ישנים מ-20 שעות. זמן בדיקה בעתיד נחשב טרי. כשאי אפשר לקרוא את הריצות, ממתינים לבדיקה הבאה; GitLab והתראת הטריות נשארים כגיבוי.

סריקת פרסום נספרת מרגע שהצעד בשם `scrape` התחיל, לפי זמן ההתחלה של הצעד; עבודה שהסתיימה בלי שהצעד התחיל אינה נספרת. סריקה שעדיין ממתינה שומרת מקום רק בהחלטת `decide`, לפי זמן יצירת העבודה. עבודת `scrape` לבדה מחזיקה בנעילת `nightly`; היא מתחילה ב-checkout ובהכנת Node, ואז בודקת שוב ריצות אחרות שהסריקה בהן התחילה בפועל. ה-checkout של בדיקה אוטומטית, מ-GitLab או מה-cron, לוקח את ה-commit העדכני ביותר של main, ולכן הבדיקה החוזרת קוראת את הנתונים העדכניים גם אחרי המתנה לנעילה. כך בדיקות שהגיעו יחד אינן מתחילות שתי סריקות. יתר הצעדים, כולל הדוח ושמירת המטמון אחרי כישלון, מותנים באישור הבדיקה החוזרת. ריצות ידניות מסוג `workflow_dispatch`, כולל הפעלה חוזרת של ריצה (Re-run ב-Actions), עוקפות את שתי הבדיקות; הנעילה עדיין מונעת שתי סריקות במקביל. smoke ו-dry_run מקבלות שמות נפרדים ואינן נספרות כסריקות פרסום. ריצה ממתינה חדשה יכולה להחליף ריצה ממתינה ישנה.

הפעלה חוזרת ידנית של ריצה שנוצרה לפני יותר מ-24 שעות אינה נספרת, ולכן הסריקה הבאה יכולה להתחיל פחות משלוש שעות אחריה, אך לא במקביל לה בזכות הנעילה.

סריקת הלילה קוראת מחדש את כל הדפים, כולל דפי קורס ורשימות. בחלון אחר הצהריים, כשזמן הבדיקה של הנתונים שפורסמו אינו ישן מ-20 שעות, הסריקה קלה וקוראת קבוצות וטבלאות בחינות; דפי קורס ורשימות נקראים רק אם חסרו במטמון או עברו 2.5–3.5 ימים לפי המפתח. מחזורים דומים אינם מאריכים את הזמן. כשהנתונים ישנים מ-20 שעות, חסרים או לא תקינים, גם אחר הצהריים והשלמה מחוץ לחלונות קוראים הכול. ריצה ידנית, כולל הפעלה חוזרת, smoke ו-dry_run, קוראת הכול במסגרת ההיקף שלה. סוג הריצה נקבע מחדש תחת הנעילה בפלט `full`; כשהוא `true` ואין במטמון ששוחזר קובץ `partial-runs`, צעד הסריקה מעביר `--refresh-pages`. המשך אחרי ריצה חלקית מתבצע כסריקה קלה, כמפורט בהמשך. ההחלטה אינה תלויה בגיל דפי המטמון, ולכן אחרי סריקה מלאה שהסתיימה אחר הצהריים, הלילה הבא קורא שוב את דפי הקורס. כשהריצות מצליחות, הפיגור אחרי הידיעון הוא כיממה.

לילה מלא כולל כ-1650 בקשות בסיס: 676 רשימות, כ-396 קבוצות, כ-573 דפי קורס, 7 טבלאות בחינות ו-2 בקשות פתיחת חיבור. משכו כארבע שעות; אחר צהריים קל כולל כ-405 בקשות ונמשך כשעה. יחד מדובר בכ-2000–2100 בקשות בסיס ביום, בתוספת המתנות למגבלה וניסיונות חוזרים. אין מכסת תשובות בריצה: הסורק שומר על קצב הבקשות וממתין למגבלה השעתית של הידיעון, כ-400 תשובות בשעה. לילה שהתחיל מאוחר יכול להימשך גם בזמן בדיקת הגיבוי ב-07:07; במקרה כזה GitLab מזהה ש-GitHub עסוק וממתין.

בכל שבת לפי שעון ישראל, רק סריקת הפרסום האוטומטית, מ-GitLab או מה-cron, בחלון הלילה על main מתחילה בלי מטמון, לפי פלט `cold` שנקבע בבדיקה החוזרת תחת הנעילה. אחר הצהריים וסריקת השלמה מחוץ לחלון הלילה משחזרים כרגיל. ריצה חלקית שומרת את ההתקדמות במטמון; הריצה הבאה שמשחזרת אותו ממשיכה ממנו כסריקה קלה, גם אם פלט `full` הוא `true`. אחרי ריצה שהסתיימה במלואה, הסריקה המלאה הבאה חוזרת לקרוא מחדש את כל הדפים. ריצות smoke, ענף ו-dry_run משחזרות כרגיל. קידומת המטמון לפרסום נשארת `yedion-night-v2-`.

בשני השירותים נקרא דף קורס אחד לכל סמסטר שיש בו קבוצה ראשית עם קישור תקין. נ״ז ודרישות קדם באים מהדף הראשון, ומועדי הבחינות מהדף של כל סמסטר. הקדימות נשארת: טבלה רשמית, דף קורס שאינו ישן מהמשיכה הידנית, ואז המשיכה הידנית.

אחרי הסריקה, GitHub מבצע commit ו-pull עם rebase ודוחף בעזרת GITHUB_TOKEN. הוא מפעיל במפורש את deploy.yml ואת checks.yml, כי דחיפה בטוקן הזה לא מפעילה workflows. מרוץ מול דחיפה אחרת מקבל עד שלושה ניסיונות; סתירת rebase מבטלת אותו ומכשילה את הריצה כדי שתישלח התראה. ריצה בלי שינויים לא מפרסמת ולא מפעילה פריסה. ריצה ידנית עם dry_run סורקת ומפעילה deploy ו-checks על main בלי commit, דחיפה או העלאת seed; smoke סורק תוכנית וסמסטר אחד עם מטמון נפרד, ולעולם אינו מבצע commit, דחיפה, העלאת seed או הפעלת workflows, גם עם dry_run.

**GitLab נשאר גם גיבוי לסריקה:** ב-[ci/gitlab-scrape.yml](../ci/gitlab-scrape.yml) לוח הגיבוי, בלי `ROLE`, בודק ב-07:07 וב-13:07 בישראל: cron `7 7,13 * * *`, אזור זמן `Asia/Jerusalem`. בדיקת הגיבוי עולה כחצי דקה. קודם נבדק אם יש ריצת nightly.yml לא גמורה על main, מסוג schedule, repository_dispatch או workflow_dispatch, שנוצרה בשש השעות האחרונות, מתוך עד 100 ריצות אחרונות; אם כן, ממתינים. גם ריצה שעדיין רק בודקת אם הגיע הזמן נחשבת עסוקה. אחרת, נתונים צעירים מ-12 שעות משאירים את GitLab בהמתנה; מגיל 12 שעות הוא סורק ומפרסם. הסף הוא `STANDBY_HOURS=12`. זמן בדיקה חסר או לא קריא גורם לסריקה, אלא אם GitHub עסוק. כישלון בבקשת הריצות נחשב שאין ריצה עסוקה; כישלון בבקשת המצב נחשב זמן בדיקה חסר. לכל בקשה מגבלת 20 שניות. הבדיקה בצהריים תופסת ריצת בוקר שהייתה עסוקה ואחר כך נכשלה. אחרי תקלה ממושכת ב-GitHub, סריקת השלמה שלו והשתלטות GitLab עלולות לחפוף: אין נעילה משותפת, והדחיפה של GitLab משתמשת ב-rebase.

רק אחרי דחיפה מוצלחת, GitHub מעלה את תשובות הידיעון הציבוריות ל-cache.tgz ב-pre-release בשם cache-seed. כשל בהעלאה נרשם ואינו מכשיל פרסום שכבר הצליח. אחרי שהשער החליט לסרוק, GitLab מוריד את ה-seed ומחלץ לבדיקה לתיקייה זמנית; החלפה דורשת סמני published-at תקינים בתיקיות השנים של ה-seed, וחדשים ממש מכל סמן מקומי מקביל, אם קיים. שנה מקומית שחסרה ב-seed, סמן שווה או ישן, או סמן לא תקין משאירים את המטמון הקיים עם שורת הסבר; גם הורדה או חילוץ שנכשלו משאירים אותו וממשיכים. ה-seed מאפשר פרסום כבר בהשתלטות הראשונה, בהערכה כ-15 דקות; בלעדיו ייתכן שהסריקה תמתין עד שהמטמון ישלים את הפיגור. GitLab ממשיך למשוך חצי מהקורסים בכל לילה, במסגרת 380 תשובות ישנות בריצה, כדי להתאים למכסת הדקות שלו. ל-commit שלו מתווספת הפסקה `GitLab standby run`. GH_PUSH_TOKEN נשאר בגיבוי, מחודש מדי שנה, ובדיקת התוקף שלו נשארת (הסעיף הבא). כדי לכפות סריקה ידנית: Build → Pipelines → Run pipeline; ריצה ידנית עוקפת את שער ההמתנה.

זמני GitLab נשארים כפי שהיו: דפי קורס 14–16 ימים, רשימות וטבלאות בחינות מלאות 7–9 ימים, וטבלאות ריקות 1.5 ימים. כלל המחזורים הדומים נשאר, וכן מכסת 160 תשובות ישנות לרשימות ולדפי קורס בתוך המכסה הכוללת של 380.

GitLab Free נותן 400 דקות CI בחודש. שש שליחות ביום, כחצי דקה לכל שליחה, עולות כ-90 דקות בחודש. בדיקת גיבוי עולה כחצי דקה, פעמיים ביום, כלומר כ-30 דקות נוספות בחודש אם לוח הגיבוי פעיל. השתלטות עולה כ-15–20 דקות. פרויקט GitLab ציבורי ולכן גם יומני העבודות ציבוריים; הטוקן לעולם אינו מודפס ומשתני ה-CI נשארים סודיים.

**קריאת הבוקר:** קוראים את השלב report ב-Actions: שורת הסיכום, הקבצים שהשתנו, וספירת דחיות, שגיאות רשת והמתנות למגבלה. הדוח נכתב גם לסיכום באתר וגם ליומן, שאפשר לקרוא עם `gh run view --log`. אחריו מופיעות 300 השורות הראשונות של ההבדלים, בלי status.json שמשתנה בכל ריצה. מטמון התשובות נשמר גם אחרי כישלון. timeout של 320 דקות ב-GitHub ושל 160 דקות ב-GitLab משאיר את המטמון להשלמה בריצה הבאה; הריצה החלקית הרביעית ברצף נכשלת ושולחת התראה.

**טריות והתראות:** האתר מזהיר אחרי 18 שעות, כי בשני חלונות פרסום ביום זה סימן שריצה הוחמצה. freshness.yml בודק ב-05:41 וב-17:41 UTC ונכשל אחרי 30 שעות, או כשזמן הבדיקה חסר או לא קריא: שתי ריצות הוחמצו או פריסה נכשלה. לבדיקת המייל מריצים אותו ידנית עם hours=0. כישלון של ריצה מתוזמנת שולח מייל למי שערך אחרון את שורות ה-cron, אם התראות Actions פעילות. GitHub יכול לעכב ריצות או לדלג עליהן, במיוחד בראש השעה, ולכן הבדיקה השעתית מתוזמנת לדקה 37. הוא מכבה לוח זמנים אחרי 60 יום בלי פעילות בריפו; ה-commits של הריצות המתוזמנות, כולל checkedAt גם בלי שינוי בקורסים, שומרים על פעילותו.

**ריצה שנעצרה בבדיקת נתונים:** הסורק לא כותב כשהנתונים נראים שבורים: ירידה חדה בכמות או שגיאת נתונים חדשה, למשל מעגל בדרישות קדם. האתר נשאר על הנתונים הקודמים; בסמסטר הקיץ נשמר רק הקובץ הישן שלו. מתקנים את הסורק אם הטעות בו. אם כך כתוב בידיעון ויש צורך לפרסם בכל זאת, מריצים את GitLab ידנית עם המשתנה SCRAPE_ARGS בערך --force. checks.yml ממשיך לדווח על שגיאות הנתונים.


## חידוש GH_PUSH_TOKEN

הסריקה דוחפת ל-GitHub עם טוקן fine-grained שיש לו תאריך תפוגה; אותו טוקן משמש גם לשליחת `pull-check`. העבודה `token-expiry` ב-[ci/gitlab-scrape.yml](../ci/gitlab-scrape.yml) נכשלת, ושולחת מייל, כשנשארים פחות מ-14 יום, וגם כש-GitHub דוחה את הטוקן (פג או בוטל). הסריקה עצמה ממשיכה לרוץ. בלוח עם `ROLE=dispatch` העבודה הזו אינה פועלת; במקומה `dispatch` בודקת את התוקף בשעה 01 בישראל, מתוך כותרת התשובה לשליחה. כדי לחדש:

1. ב-GitHub: Settings → Developer settings → Fine-grained tokens → Generate new token.
2. Resource owner: הארגון `lets-learn-il` (לא החשבון האישי). Repository access: רק `lets-learn-il/lets-learn-il.github.io`. Permissions: Contents, Read and write. לבחור תאריך תפוגה.
3. ב-GitLab, בפרויקט `lets_learn-scrape`: Settings → CI/CD → Variables → `GH_PUSH_TOKEN` → להדביק את הטוקן החדש (Masked and hidden, Protected).
4. בלוח הגיבוי: Build → Pipeline schedules → ▶ כדי להריץ פעם אחת; ביומן של `token-expiry` מופיע התאריך החדש. בלוח השליחה, התאריך מופיע ביומן של `dispatch` רק בשעה 01 בישראל; בכל שעה אחרת נבדק שקוד התשובה הוא 204. הפעלה דרך לוח השליחה עשויה להתחיל סריקה אם בדיקות הזמן והנתונים מאפשרות זאת.
5. למחוק ב-GitHub את הטוקן הישן.

## מעבר שנת לימודים

האתר לוקח את השנה האקדמית מ-`catalog.json`, שהסורק כותב, והמטמון נשמר בתיקייה נפרדת לכל שנה (`.yedion-cache/2028`). כשהידיעון של השנה הבאה מתפרסם:

1. משנים את ברירת המחדל של `--year` ב-`scripts/scrape.mjs`.
2. ב-`scripts/programs.json`, לכל תוכנית: מוסיפים את המחזור החדש ל-`cohorts` ואת קודי הרשימות שלו ל-`lists`, ומורידים את המחזור הישן.
